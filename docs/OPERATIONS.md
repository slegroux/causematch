# Operations

Everything needed to configure, run, secure and deploy Causematch: environment variables, scheduled jobs, the security model, front-end assets, the demo, the preview deploy, schema changes, the secret scan and admin tasks. For what the app does, see the [README](../README.md); for how it is built, see [ARCHITECTURE.md](ARCHITECTURE.md).

## Configuration

Environment variables (`.env.example` lists them all, without values). The app refuses to start in production without:

- `CAUSEMATCH_ENV`, `SESSION_SECRET`, `PUBLIC_BASE_URL`, `TASKS_TOKEN`
- `EMAIL_API_KEY`, `EMAIL_FROM` (Resend), or `SMTP_USERNAME`, `SMTP_PASSWORD` (see Email through Gmail): email, which is also every volunteer's way in (the emailed link), with Google and Apple optional beside it (see below)
- `CONTACT_EMAIL`: the address on the privacy page
- `PHONE_HASH_KEY`: keys the hashes kept of a deleted account's phone and of its Google or Apple accounts when a block, report or suspension must outlive it, the rate-limit hashes, and the urgent unsubscribe links
- `CERTIFICATE_KEY`: signs volunteers' hour certificates (HMAC); changing it makes every certificate issued before read as not genuine, so keep it like `SESSION_SECRET`
- `TRUSTED_PROXY_HOPS` on Cloud Run (see Security)

`SESSION_SECRET`, `PHONE_HASH_KEY`, `CERTIFICATE_KEY` and `TASKS_TOKEN` must be at least 32 random characters in production, and `PUBLIC_BASE_URL` an `https://` origin with no path.

#### Rotating `CERTIFICATE_KEY`

Don't, without a plan. Every certificate's signature is checked against the current key, so changing it makes every certificate issued before read "Not a Causematch record" on its check link, and its PDF download is refused. Back the production key up where the other secrets are kept. Keeping an old key for verification (checking against the old and the new) is not built; build it before any rotation.

Volunteers sign in with the emailed link (email, above), or with Google or Apple when configured; `config.require_volunteer_sign_in` refuses a production start with none of them (on a preview, the fake emailer counts). A phone number is never a way in. Each of these is optional on its own, but one set halfway refuses to start:

- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`: both or neither. The secret must be at least 32 characters in production (Google's are).
- `APPLE_CLIENT_ID` (the Services ID), `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`: all four or none. The key must be the `.p8` file's EC P-256 PEM, else the app refuses to start without quoting it; literal `\n` sequences in it are turned back into newlines. Apple sign-in works only over https. Without them there is no Apple button, even with the fake below.
- `CAUSEMATCH_FAKE_OAUTH`: a local consent page stands in for a provider. `1` is Google alone (what `scripts/demo.py` and the preview deploy set); a list such as `google,apple` names each one (the tests). Development, test and preview only; production refuses to start with it.
- `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_NUMBER`: all three or none, for texts (match news, messages, shift reminders, last-minute calls) to a volunteer who has a number. `TWILIO_VERIFY_SID` is optional on top: with it, Me offers "add a number", which texts a code through Twilio Verify and saves the number only once the code checks out; without it Me offers nothing and `/me/phone/send` and `/me/phone/verify` answer 404. Without Twilio volunteers get all of it by email.

Setting the providers up is in Security, Live providers.

### Email through Gmail (beta)

Until there is a domain to send from with Resend, every email (volunteers' and staff's sign-in links, notices) can go through a free Gmail account over SMTP. `notify.make_emailer` uses Resend whenever `EMAIL_API_KEY` is set, else SMTP when `SMTP_USERNAME` and `SMTP_PASSWORD` are; SMTP set halfway refuses to start. The connection is always TLS with the certificate checked (STARTTLS on 587, TLS from the start on 465); a server without STARTTLS is refused, and there is no plain SMTP. Each send has 30 seconds in all (`notify.SMTP_DEADLINE`), the connect, the TLS handshake, the greeting (it must be 220) and signing in included. A send that runs out of time once the message may have reached Gmail is recorded `unknown` and never retried; one that fails before that is recorded `failed`, for the hourly sweep to retry. After a timeout or a failed connect, no connect is tried for 60 seconds (`notify.SMTP_BREAK`): sends in that minute fail at once, spending nothing. The sweeps and the emails to an org's coordinators share one signed-in connection. Notices a request triggers (a like, an accept, a withdrawal, a cancelled shift) go out after its response (`notify.after`), at most 4 at a time (`notify.AFTER_LIMITER`, apart from the threads the routes run in); sign-in links already did. An admin's claim emails stay in the request, since the page says whether they went.

**The account is admin-equivalent.** Anyone signed in to it, or holding the app password, could read the Sent folder: every recipient's address and live sign-in links, staff's and admins' included. Keep the people who hold its password and second factor to the one or two who hold production's secrets.

1. Create a Gmail account for the app alone (for example `causematch.example@gmail.com`), never a person's.
2. Turn on 2-Step Verification for it (Google Account, Security). App passwords need it.
3. In Gmail, Settings, See all settings, Forwarding and POP/IMAP: disable POP, disable IMAP if the page still offers it (Google has been making IMAP always on), and save. Sending needs neither. Where IMAP can't be turned off, the app password can read the mailbox, which is one more reason for step 6.
4. Create an app password named `Causematch` (Google Account, Security, App passwords). Google shows 16 letters once, in four groups.
5. Put it in Secret Manager. `read -rs` keeps it out of the shell history and off the screen; paste it and press Enter, and `tr` drops the spaces between the groups:

   ```sh
   read -rs SMTP_PASSWORD_VALUE
   printf %s "$SMTP_PASSWORD_VALUE" | tr -d ' ' | gcloud secrets create SMTP_PASSWORD \
     --project causematch-la --replication-policy=automatic --data-file=-
   unset SMTP_PASSWORD_VALUE
   gcloud secrets add-iam-policy-binding SMTP_PASSWORD --project causematch-la \
     --member="serviceAccount:$SERVICE_ACCOUNT" --role=roles/secretmanager.secretAccessor
   ```

   `SERVICE_ACCOUNT` is the account the Cloud Run service runs as. A new password later is `gcloud secrets versions add SMTP_PASSWORD --data-file=-` the same way, then a redeploy.
6. Empty the mailbox every day: Gmail keeps a copy of every email sent through it, and bounces and replies land in the Inbox. Signed in as the account, open [script.google.com](https://script.google.com), New project, name it `Purge mail`, and paste:

   ```js
   function purgeMail() {
     const query = 'in:anywhere -in:trash older_than:1d';  // Sent, Inbox, Spam: all of it
     let threads = GmailApp.search(query, 0, 100);
     while (threads.length) {
       GmailApp.moveThreadsToTrash(threads);
       threads = GmailApp.search(query, 0, 100);
     }
   }
   ```

   Save, run `purgeMail` once and grant it access to Gmail, then Triggers, Add Trigger: `purgeMail`, time-driven, day timer, any hour. Gmail erases the bin's contents after 30 days. **Then set `GMAIL_PURGE=daily`** on the service: only with it does the privacy page say copies go after a day. Without it the page says they stay in the account until deleted or the account is closed, which is true when nothing purges them; a manual purge doesn't count, so don't set it for one.
7. Deploy. The checklist, beyond the other secrets:
   - `SMTP_USERNAME` set to the account's address (an env var: it isn't secret), and the password from Secret Manager: `--set-secrets SMTP_PASSWORD=SMTP_PASSWORD:latest`. Leave `EMAIL_API_KEY` unset.
   - **`--max-instances 1`.** The ceilings below are counted in the instance's SQLite file, so a second instance would have its own count, and Gmail's limit is per account.
   - **`--no-cpu-throttling`** (CPU always allocated, which is instance-based billing). Sign-in links and notices are sent after the response, and with the default request-based billing Cloud Run throttles the CPU once a response is out, so those sends can stall or be cut off. The trade-off is cost: an instance with CPU always allocated is billed for its whole life (all the time with `--min-instances 1`), not only while it serves requests. The deploy scripts don't set it; decide at deploy. Without it, expect some links and notices to arrive late or not at all.
   - `GMAIL_PURGE=daily` once step 6's trigger runs.

The variables: `SMTP_USERNAME` (the Gmail address), `SMTP_PASSWORD` (the app password; at least 16 characters in production), `SMTP_HOST` (default `smtp.gmail.com`), `SMTP_PORT` (default 587), `SMTP_MAX_PER_DAY` (default 400, at most 450 through `smtp.gmail.com`, a margin under Gmail's 500), `GMAIL_PURGE` (`daily` or unset, see step 6). All whitespace is dropped from `SMTP_PASSWORD`, which assumes a Gmail app password (it has none of its own): another provider's password with a space in it would break. From is `EMAIL_FROM` when set, else `SMTP_USERNAME`; Gmail rewrites From to the account signed in anyway, so only a display name such as `Causematch <causematch.example@gmail.com>` is worth setting there. A failed send logs only the exception's type, never the password, the address or the link.

**The daily limit.** A free Gmail account sends to about 500 recipients a day, and Google may lock an account that goes over. The app counts every email sent over SMTP against `SMTP_MAX_PER_DAY` in any 24 hours (the `rate_event` table, as the SMS ceiling), and each kind against a share of it (`notify.NOTICE_SHARE` and the others):

| Kind | May use |
|---|---|
| everything but staff's sign-in links (volunteers' links, sign-ups, every notice) | 90% |
| notices (matches, messages, reminders, likes, cancellations, claim decisions), within that | 50% |
| last-minute calls' emails, among the notices | 25% |
| sign-up links (an address no account holds), within the 90% | 25% |
| staff's sign-in links (`send_login_link`, from `/org/login` or `/login`) | the whole: the last 10% is theirs alone |

The existing ceilings don't keep under Gmail's limit on their own: sign-up links alone may reach 500 a day. While email goes through Gmail, `/login` also allows each mailbox only 5 links a day (`security.LINK_PER_EMAIL_SMTP`, beside the 20 that `/login` and `/org/login` share), so a handful of accounts can't spend the volunteers' share, and whatever they do, staff keep their 10%. One volunteer's likes email the orgs for 20 likes a day (`security.LIKE_NOTICES`); later likes show in the org's inbox only. Past a ceiling nothing is sent (a sign-in link is lost, a notice is recorded `failed`) and each refusal logs a warning naming it: `rate limit reached: email-smtp-day` (everything), or `email-smtp-public-day`, `email-smtp-notices-day`, `email-smtp-urgent-day`, `email-smtp-signups-day` in its place.

**Alerts.** Make three log-based alerts in Cloud Logging:

- `textPayload:"rate limit reached: email-smtp"`: a share or the whole ceiling ran out. Notices or sign-ups are being dropped, or, for `email-smtp-day`, people are not getting their sign-in links. Either way it is time to move to Resend.
- `textPayload:"SMTPAuthenticationError"` (it appears as `sending a sign-in link failed: SMTPAuthenticationError`, or `... notification failed: SMTPAuthenticationError`): Gmail refused the app password. It was revoked, the account's password changed (which revokes app passwords), or Google locked the account. Nobody gets email until it is fixed: make a new app password and add it as a new secret version.
- `textPayload:"SMTPSenderRefused" OR textPayload:"SMTPDataError"`: Gmail refused a message after signing in, most often because the account hit Google's own daily sending limit (it says so in a 550 or 554 reply, which isn't logged) or was flagged for spam. Expect it to clear within 24 hours; if it recurs, lower `SMTP_MAX_PER_DAY` or move to Resend.

**Spam.** Mail from a fresh Gmail account to many new recipients, all carrying links, is what spam filters look for: expect some sign-in links in spam or Promotions, more so at volume, and tell beta testers to look there. Don't buy volume by adding Gmail accounts: this is a stopgap until Resend.

**Moving to Resend later** is configuration only: verify the sending domain in Resend, set `EMAIL_API_KEY` (a secret) and `EMAIL_FROM` (an address on that domain), and redeploy. With `EMAIL_API_KEY` set Resend is used and SMTP's settings are ignored (still checked, so remove them all, or leave them all), and the privacy page names Resend. Then delete the `SMTP_PASSWORD` secret, the app password and the Apps Script trigger, unset `GMAIL_PURGE`, and empty the account's mailbox and bin.

### Scheduled jobs

The host scales to zero, so nothing runs in the background: Cloud Scheduler is to call two endpoints with `Authorization: Bearer $TASKS_TOKEN` (anything else gets 401).

> **Not set up yet.** No scheduler jobs exist today, so shift reminders, retries and urgent waves don't go out on their own. Create the jobs below as part of the production launch. A preview can't be called this way at all: its password gate reads the same `Authorization` header, so a preview would first need `/tasks/*` exempted from `PreviewGate` or the token moved to its own header.

| Job | Schedule | Does |
|---|---|---|
| `POST /tasks/reminders` | hourly (`0 * * * *`) | shift reminders 23 to 25 hours ahead, retries of failed or deferred "you're matched" and message texts, and blanking decided claim requests |
| `POST /tasks/urgent` | every 10 minutes (`*/10 * * * *`) | urgent calls' notification waves: wave 1 at the first run after a call is posted, wave 2 thirty minutes later if it hasn't filled |

```sh
gcloud scheduler jobs create http causematch-urgent --location=$REGION \
  --schedule='*/10 * * * *' --time-zone=America/Los_Angeles \
  --uri="$PUBLIC_BASE_URL/tasks/urgent" --http-method=POST \
  --headers="Authorization=Bearer $TASKS_TOKEN"
```

The reminders job is created the same way, with `--schedule='0 * * * *'` and `/tasks/reminders`.

## Security

`app/security.py` holds the request-level defences; `security.Guard` wraps the whole app, ahead of sessions and Beforeware.

- **Same-origin writes.** Every POST/PUT/PATCH/DELETE must carry an `Origin` equal to `PUBLIC_BASE_URL`'s origin (or, with no `Origin`, a `Referer` on it), else 403. This covers the public sign-in and claim forms too. Only `/tasks/*` (Cloud Scheduler sends a bearer token and no `Origin`) and `POST /auth/apple/callback` (Apple posts it from its own origin, see Sign-in) are exempt. Websocket handshakes need the exact `Origin`, else they are closed with 1008.
- **Headers** on every response: a CSP allowing only this origin (`script-src 'self'`, `style-src 'self'`, no inline code), `X-Frame-Options: DENY`, `nosniff`, a referrer policy, a permissions policy, `Cache-Control: no-store` outside `/static` and `/favicon.ico` (unless a route sets its own, as photos do), and HSTS in production.
- **Rate limits.** Sending sign-in links and Me's add-a-number codes, OAuth callbacks, wrong code checks, claims and ProPublica calls are counted in the `rate_event` table (keyed by a hash, never the phone, email or IP), so a restart doesn't reset them; swipes, chat, report/block posts and photo uploads use in-memory token buckets per user. Over an HTTP limit: 429 and a warning naming it (chat frames over the bucket close the socket with 1013). Sign-in links are counted, shared between `/login` and `/org/login`, for every well-formed address whether or not an account holds it (`security.link_limits`): per mailbox and client address (5 an hour), per mailbox (20 a day), per client address (20 an hour) and per IPv6 /48 (40 an hour). A mailbox is `forms.abuse_key`: lowercased, without a `+tag`, and for Gmail without dots and under `gmail.com`, so writing an address another way doesn't buy more. Sign-up links (to an address no account holds) also have an app-wide ceiling, `security.SIGNUP_ALL`, of 100 an hour and 500 a day, since each costs email and bounces can get the sender suspended; it is checked when sending, after the page has answered, so a visitor sees nothing different, and sign-in and staff links don't count against it. Reaching it is silent to visitors: new people simply get no sign-up email. **Alert on it**: the log says `rate limit reached: signup-all-hour` (or `signup-all-day`), so set a log-based alert in Cloud Logging on those warnings. Add-a-number codes are counted per (phone, client address), per phone per day, per address, per IPv6 /48, and against a ceiling on every text the app sends (`SMS_MAX_PER_HOUR`, default 100; `SMS_MAX_PER_DAY`, default 500). A notification text over the ceiling is recorded `deferred`; the reminders task (planned hourly, see Scheduled jobs) resends deferred "you're matched" and message texts, and a later urgent run retries a deferred urgent notice.
- **Client IP.** `TRUSTED_PROXY_HOPS` says how many addresses the proxies in front append to `X-Forwarded-For`: the client is that many places from the right, and anything further left (whatever the client sent) is ignored. 0, the default, uses the socket peer. On Cloud Run it must be set: 1 for the plain `*.run.app` URL, 2 behind an external Application Load Balancer. IPv4-mapped IPv6 counts as IPv4; IPv6 clients are counted per /64. With `CAUSEMATCH_LOG_LEVEL=DEBUG` each limited request logs a hashed client key (never the address), for checking the setting after a deploy.
- **Bodies** over 64 KB get 413, except on the photo upload paths (`security.UPLOADS`), which take up to 6 MB.
- **Photos** (`app/photos.py`) are decoded by Pillow and re-encoded as fresh JPEGs, so no EXIF, GPS or other metadata survives and the browser never gets the uploaded bytes. The size is read from the header and refused past a per-format cap before decoding (JPEG 50 MP, WebP 8 MP, PNG/GIF 12 MP); a JPEG's marker stream is walked first and refused unless it is plain (baseline, extended or progressive, at most 50 scans, a coefficient budget for multi-scan files, no stray bytes). The decode itself runs in a child process (`app/photo_worker.py`, about 60 ms per upload), at most two at a time, with an environment of `PATH` and `LANG` only (no secrets): it is killed after 10 s or past 4 MB of output, it can't dump core, and on Linux it also runs under `RLIMIT_AS` (512 MB) and `RLIMIT_CPU` (8 s); macOS doesn't enforce `RLIMIT_AS`, so development has the CPU limit and the timeout only. The child runs as the same user: it limits resources, it doesn't drop privilege. A WebP's size is read from its header in Python, so the app process itself never runs libwebp on an upload. A decode shrinks at once to 4 MP, so one upload stays under about 200 MB. Uploads share a per-user bucket (10, then one a minute). The bytes live in SQLite (the `photo` table), so a database backup covers them too. They are stored under unguessable keys, served at `/photos/{key}.jpg` with an access check: a volunteer's photo only to themselves, an admin, and a nonprofit whose inbox shows one of their matches, with no block either way (`data._sees_volunteer`); anyone else gets 404. Give Cloud Run at least 1 GiB of memory for two worst-case decodes at once. In production an error is a plain 500 page with a reference, and the log line has the request id and stack frames but not the exception's message (it can hold a phone number).
- **Development mode is for localhost only:** its session secret is public, its fake SMS accepts `000000` (Me's add-a-number), its fake emailer logs sign-in links, and its fake Google (and Apple, when named) page signs anyone in as any account. Production refuses all three.
- **Preview** (`CAUSEMATCH_ENV=preview`, also on Cloud Run) is production behind a password: the same secrets, cookie, HSTS and checks, plus `PREVIEW_PASSWORD` (at least 16 characters, else the app refuses to start). `security.PreviewGate`, just inside `Guard`, lets nobody in without it, on every request: pages, `/static`, `/photos`, `/tasks` and websockets. The link to send is the service URL with `?access=<PREVIEW_PASSWORD>`. On a top-level navigation (or from curl, which sends no Sec-Fetch headers) a GET with the right key (constant-time compare) gets a 303 to the same path and query without the key, and the cookie `__Host-cm_preview` (Secure, HttpOnly, SameSite=Lax, Path=/, 30 days). The cookie holds its issue time and an HMAC-SHA256 keyed with `SESSION_SECRET` over the password's digest and that time, so it can't be made without the secret, is refused after 30 days, and a new password voids every one. A request with `?access=` that isn't a navigation (an `<img>` on another site, say) is refused without weighing or counting the key, and a browser that already has the cookie just gets the 303 without the key. The cookie lets the browser in from then on, websocket handshakes included; HTTP Basic auth with the password (any user name) still works, for scripts and `curl -u`. Anything else gets a plain 401 page ("This is a private preview. Ask the Causematch team for the link.") with no `WWW-Authenticate`, so browsers show no password dialog; websockets are closed with 1008. Wrong keys, wrong or expired cookies and wrong Basic passwords are counted per client address (10, then one a minute; past that 429 without checking, for everyone there without a valid cookie: a valid one still gets in, since it can't be made without the secret); a wrong cookie is also deleted, so it counts once. The app's access log redacts the key (`security.RedactTokens`), but Cloud Run's own request log records the full URL of the link's first request, key included: anyone who can read the project's logs can read the password. To revoke every link and cookie, rotate the password. Make the password with `python -c 'import secrets; print(secrets.token_urlsafe(24))'`: random, and URL-safe, so the link needs no percent-encoding. Send the link by direct message, not in a channel or document that unfurls links (an unfurler fetches it and logs the URL too). Only `/robots.txt` answers without it (`Disallow: /`), and every response carries `X-Robots-Tag: noindex, nofollow`. A preview may use the fake SMS, emailer and Google page (`CAUSEMATCH_FAKE_OAUTH=1`, which the deploy script sets: Google alone, so no Apple button), shows a "Preview" banner on every page, seeds the demo's data into its empty database at startup (`app/demo_seed.py`: `PREVIEW_SEED_DIR`, else the invented orgs), logs the demo coordinator's and admin's sign-in links, and shows a new sign-in link on the page instead of emailing it: a coordinator's on `/org/login`, a volunteer's (or a coordinator's) on `/login` (an admin's stays in the log, with the address masked). Production refuses all of these. **A preview is demo-only, and the code enforces it** (`config.demo_address`, `config.demo_number`): the on-page link, the logged link (on `/org/login` and `/login`) and the fake Google page for coordinators work only for addresses at `@demo.causematch.test` and `@team.demo.causematch.test`, and any other address gets the unknown address's answer ("If that address belongs to a coordinator, a sign-in link is on its way") with nothing sent or logged, even for a real coordinator approved there. The fake code goes only to the fictional numbers 555-0100 to 555-0199, in any area code; any other number in Me's add-a-number gets "This preview uses demo numbers only, like (310) 555-0100." and no code. The fake consent page's subject starts blank and is required, so testers don't share one account by keeping a default. The banner says the data is demo data, wiped at any time.
- **Session cookie:** `__Host-cm_session` in production (Secure, HttpOnly, SameSite=Lax, Path=/), `cm_session` in development.

Run the app with the flags in the `Procfile` (`--ws-max-size 65536`, `--limit-concurrency 200`, ...); `python main.py` uses the same ones.

### Sign-in

`app/routes/auth.py` holds the volunteers' emailed link and `app/routes/org_auth.py` the staff's; `app/oauth.py` holds the Google and Apple flow and its checks, and `app/routes/oauth.py` its routes.

- **Who uses what.** Volunteers sign in at `/login` with an emailed link, or Google or Apple when configured, and the first sign-in creates the account. A number on the profile only gets texts.
- **The volunteer's emailed link.** `POST /login/send` takes an address (ASCII, at most 254 characters, a bare `local@domain` as `forms.EMAIL` reads it: no display name, angle brackets, quotes or trailing dot; else "Enter your email address" with nothing counted), lowercases it, counts it (above), and always answers the same "Check your email" page; the email goes out after the response, so every address takes the same time. What is sent (`data.volunteer_link_kind`): a sign-in link to a live volunteer who signed up with the address, a sign-up link to an address no account holds, nothing to a mailbox (`forms.abuse_key`) that a suspended account holds as a verified address by any way in, email link, Google or Apple, live or deleted with its hash kept, and to a coordinator's or admin's address the staff link `/org/login` sends (one address, one role: a staff address never becomes a volunteer, and a suspended or org-less one gets nothing). The token is 32 random bytes, stored as its SHA-256 with the lowercased address and no profile (`login_token.email`), works once, expires in 15 minutes, and a new one replaces the last. `GET /login/verify` consumes nothing: it moves the token into the session and redirects to the same path without it (`Referrer-Policy: same-origin`), so a mail scanner's fetch can't use it up. The page only peeks at the token: it says "Sign in as" the address, and warns when this browser didn't ask for a link to it (the session keeps a keyed digest of the last mailbox asked for, never the address, for 15 minutes) or is signed in to another account, because pressing the button on a link someone sent you would sign you in to their account (login CSRF); `/org/login/verify` does the same. The page's button POSTs, which uses the token up and finds or creates the volunteer as a first Google sign-in does (`data.volunteer_for_identity`, with an `email` identity whose subject is the address), then rotates the session: onboarding for a new volunteer, the deck otherwise. No profile exists until then. A staff link only works at `/org/login/verify` and a volunteer's only at `/login/verify`; neither page uses the other's up. An account is the address's `email` identity, not the profile's email: a volunteer who signed up with Google, or typed an address at onboarding, gets a new account from the emailed link (and Google gets its own from an emailed-link account), as Google and Apple don't share one either. Coordinators and admins sign in at `/org/login` with an emailed link, or with Google or Apple when the provider's verified email is the one on file (`data.staff_by_email`, the lookup the link uses too) and the provider hosts that mailbox (`oauth.authoritative`): Google for a `gmail.com` or `googlemail.com` address, or a Workspace account whose `hd` claim is the address's domain; Apple for an `icloud.com`, `me.com` or `mac.com` address. Elsewhere a provider keeps an address marked verified after the mailbox has passed to someone else (a shared role address, say), so the callback answers what `POST /org/login/send` answers for that address instead: "If that address belongs to a coordinator, a sign-in link is on its way", with the link emailed under the same limits per email and per client address, and no session. Addresses that aren't ASCII never match staff, and on a preview the fake provider never signs in an admin (they get the claim page below, as `/org/login` there keeps an admin's link in the log). A provider sign-in never creates a coordinator or admin: an unknown, deleted or suspended one gets "No nonprofit account uses this email" with a link to `/org/claim`, and nothing is stored. A button shows only when its provider is configured; otherwise its `/auth/*` routes answer 404.
- **The flow.** Authorization code flow with `state` and `nonce` (256 random bits each), plus PKCE (S256) for Google. Apple has no PKCE: its proof is the client secret, an ES256 JWT signed with the Sign in with Apple key, minted for each exchange and valid for a day. The redirect URI is always `PUBLIC_BASE_URL` plus `/auth/google/callback` or `/auth/apple/callback`, never the request's host. `fasthtml.oauth` is not used: it takes the redirect URI from the Host header and checks no state, nonce or ID token.
- **Flow cookie.** The start route sets `__Host-cm_oauth` in production and preview (`cm_oauth` elsewhere), HttpOnly, for 10 minutes, never the session. It is signed with `SESSION_SECRET`, not encrypted, and holds the provider, state, nonce, PKCE verifier and why the flow started: a volunteer signing in, a coordinator or admin signing in, or a volunteer connecting a provider (then also their id and session version). The callback refuses it unless it is ours, under 10 minutes old, for this provider and for the returned state (compared in constant time). It asks the browser to delete the cookie whatever the outcome. Nothing server-side records a used state, so a client that keeps the cookie could present it again for its 10 minutes; what makes a callback work once is the provider's one-time code (the fake's is one-time too). Callbacks are counted per client address (30 in 10 minutes, then 429), since each can call the provider's token endpoint with our client secret. Google returns by a top-level GET, so its cookie is SameSite=Lax. Apple returns by a cross-site form POST (`response_mode=form_post`), which only a SameSite=None cookie rides along on, and browsers keep SameSite=None only when Secure: Apple sign-in works only over https.
- **The one Origin exemption.** `POST /auth/apple/callback` is the only browser route exempt from the same-origin check (`security.ORIGIN_EXEMPT`), because Apple's page posts it from Apple's origin. The flow cookie stands in for the check: the callback acts only when the cookie's state matches the posted one, the code is exchanged server to server with our client secret, and the ID token must carry the cookie's nonce. A forged cross-site POST has no matching cookie and gets 400, with no session and no profile. The form's `id_token` field is ignored. Its `user` field (Apple's names, sent on the first consent only, unsigned) only names a volunteer being created by that sign-in. Every other POST, `/login/send` included, still needs our `Origin`.
- **ID token checks.** The ID token comes from the provider's token endpoint, never from the browser. It must be RS256, signed by a key from the provider's published key set (cached), with the provider's `iss`, our client id as `aud`, `exp`, `iat` and `sub` (60 s leeway), and the cookie's nonce. Then, for every kind of sign-in, `email_verified` must be true and the email present; otherwise the page says to verify the email with the provider or use the other way in. An account is the provider's `sub`, never its email: one `identity` row per provider and subject (unique), holding the email as the provider gave it.
- **A new volunteer** from Google or Apple has no phone, the provider's verified email and the given name as first name; one from the emailed link has the address and no name until onboarding. Onboarding offers the Google profile picture behind an unticked box; ticked, it is fetched once (https, a `googleusercontent.com` host, no redirects, at most the upload limit) and re-encoded like any upload. A suspended volunteer is refused, as at the emailed link.
- **Apple relay addresses.** With "Hide my email", Apple gives an `@privaterelay.appleid.com` address. Volunteers may sign in with one, and their email goes through Apple's relay, so the sending domain must be registered with Apple (Live providers below). A coordinator's relay address never matches the email on file, so they get the claim page: they should share their real email with Apple or use the emailed link.
- **Sign-in methods in Me.** `/me/profile` lists the emailed link's address (or "none") and each provider that is configured or connected: "Connected as" its email with Disconnect, or Connect. Connect (`POST /me/identity/{google,apple}/connect`) starts a flow sealed with the volunteer's id and session version. The callback connects only that volunteer, only while that session version is current, and only when the session that came with it is theirs. Apple's cross-site POST brings no session cookie (it is Lax), so there the sealed session version alone decides: signing out, a suspension or deletion since then changes it. An account already on another live profile is refused, as is a second account of the same provider. Disconnect never removes the last way in that works: it is refused unless the volunteer has another provider that is configured, or the emailed link (email is always configured). A phone never counts. The check and the delete are one statement, so two disconnects at once can't both pass. A disconnect ends every other session and open chat of that volunteer (the browser that pressed it stays signed in), because a reason to disconnect is often that the provider account is no longer only theirs. When a block, an open or actioned report or a suspension stands against the profile, the disconnected identity's keyed hash is kept as at a deletion, so signing in with it again brings them back. Connecting does not sign anyone out.
- **What deletion keeps.** Deleting an account deletes its `identity` rows and any unused link to its address. The emailed link's hash is keyed by the mailbox (`forms.abuse_key`), and a Google or Apple account also leaves one for its verified address, so a suspension or block follows an emailed-link sign-up to that mailbox. The other way round too (`data.mailbox_suspended`): a Google or Apple sign-up, or a Connect, whose verified address is a mailbox a suspended account holds (live, or deleted with its hash kept) gets a suspended profile, or is refused, and a deleted account's org blocks on that address come back. When a block, an open or actioned report or a suspension must outlive the account, `retained_identity_hash` keeps HMAC-SHA256(`PHONE_HASH_KEY`, "provider:subject") for each connected account, the emailed link's address included, on the same terms as the phone's hash, never the subject or the email. Signing up again with that account brings the suspension and the org blocks back; connecting it to another profile is refused while it is suspended and carries the blocks otherwise. Dismissing the report or lifting the block updates or drops the row, as for the phone.
- **Logs.** The app's access log redacts `token` (both emailed links'), `code` and `access`, so a link's token and a callback's code stay out of it, and a provider failure logs the exception type, never a response body. Cloud Run's own request log records Google's callback URL, code included; that code works once, expires within minutes, and is useless without the PKCE verifier and the client secret.

**Live providers.** All of their secrets go in Secret Manager, readable by the service account, as the others do.

- **Google:** in the deploy's GCP project, set up the OAuth consent screen (scopes `openid`, `email`, `profile`) and create an OAuth client of type "Web application" with the authorized redirect URI `PUBLIC_BASE_URL` + `/auth/google/callback`. Its id and secret are `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Until the consent screen is published, only its test users can sign in.
- **Apple:** it needs an Apple Developer Program membership. Create an App ID with Sign in with Apple enabled, then a Services ID with Sign in with Apple enabled and configured with that App ID, the domain of `PUBLIC_BASE_URL` and the return URL `PUBLIC_BASE_URL` + `/auth/apple/callback` (https only: Apple refuses localhost). Verify the domain if the portal asks. The Services ID is `APPLE_CLIENT_ID` and the team id `APPLE_TEAM_ID`. Create a key with Sign in with Apple enabled: its id is `APPLE_KEY_ID` and its `.p8` file, downloadable once, is `APPLE_PRIVATE_KEY`. Register the sending domain or `EMAIL_FROM` under "Sign in with Apple for Email Communication", with SPF and DKIM passing, or the relay drops mail to relay addresses. Apple sends a person's name only on their first consent; to see it again in a test, stop using the app in the Apple ID's Sign in with Apple settings.
- **Twilio** is optional, and only for texts (see Configuration).

### Front-end assets

Everything the browser loads is served from `/static`: htmx, Franken UI and daisyUI are vendored under `static/vendor/` (versions and checksums in `static/vendor/README.md`), and MonsterUI's inline theme code lives in `static/theme.js` and `static/theme.css`. Tailwind is compiled ahead of time into `static/vendor/app.css`: after adding Tailwind classes, run `scripts/build_css.sh` (it fetches a pinned, checksum-verified Tailwind CLI) and commit the result.

The design tokens (warm palette, one color per cause, the self-hosted Nunito font) are CSS variables in `static/theme.css`, also Tailwind colors (`bg-cause-food`, `text-brand`, ...) through `tailwind.config.js`. Form fields go through `app/ui.py` (`TextInput`, `Choice`, `Checks`) so each one carries its Franken UI class; `tests/test_ui.py` checks every page.

### Demo

`uv run python scripts/demo.py` serves the app on a throwaway database with demo data and prints how to sign in as a volunteer, a coordinator and an admin. It refuses production. The seeded volunteers have numbers `(310) 555-0100` (Sam) to `0103` (Priya, who has no photo); without `CAUSEMATCH_DEMO_MATCHES` Sam and Priya sign in with the emailed link to `sam@demo.causematch.test` and `priya@demo.causematch.test` (the link is in the log). With `CAUSEMATCH_DEMO_MATCHES=1`, which `demo.py` and the preview deploy set, those two have no emailed link (every visitor would share one account): instead "Try it as a volunteer" gives each visitor a fresh copy of Sam under an internal number (at most 200 at once; past that the oldest is removed), with four matches from orgs other than the demo coordinator's. Every org but the demo coordinator's has a stand-in coordinator (`team<id>@team.demo.causematch.test`) that accepts a copy's like about 4 seconds later and sends a welcome message (an ordinary volunteer's like waits, as anywhere); the demo coordinator's likes stay for a person to accept. With the switch on, `/login` also shows "Try it as a volunteer" (`POST /login/demo`: a fresh copy, 10 an hour per client address, and counted against its link limit) and `/login` and `/org/login` show "Try it as a nonprofit" (`POST /org/login/demo`: the demo coordinator, counted against the address's link limit); without it neither renders and both POSTs answer 403. Production refuses the switch at startup. `demo.py` also sets `CAUSEMATCH_FAKE_OAUTH=1`, so `/login` and `/org/login` show Continue with Google (no Apple: it isn't configured), through a fake consent page where you type the account's subject, email and names (a coordinator's email there signs in as that coordinator when Google's Hosted domain is typed as its domain; otherwise the coordinator gets the emailed link, as at `/org/login`). `--seed-file PATH` loads nonprofits from a JSON file kept outside the repo (`app/demo_seed.py`'s docstring has the format); their openings are titled "Sample: ..." and every page shows a demo banner. Logos and event photos come from `logos-raw/` and `photos-raw/` next to the seed file, read only through `photos.process` (SVG logos are skipped); every demo volunteer's photo is drawn by the script, never a real person. `scripts/screenshots.py --out DIR` screenshots every page of the same demo with Playwright.

The narrated demo video on the website (`site/assets/demo.mp4`) is rebuilt from the app itself by `scripts/video/make_demo_video.sh`; its steps and prerequisites are in [scripts/video/README.md](../scripts/video/README.md).

### Preview deploy

`scripts/deploy_preview.sh` deploys the password-protected preview (`CAUSEMATCH_ENV=preview`, see Security) to Cloud Run: service `causematch-preview` in project `causematch-la`, `us-west1`, running as the service account `causematch-preview@causematch-la.iam.gserviceaccount.com` (override with `PROJECT`, `REGION`, `SERVICE`, `SERVICE_ACCOUNT`). It needs the secrets `PREVIEW_PASSWORD`, `SESSION_SECRET`, `PHONE_HASH_KEY`, `CERTIFICATE_KEY` and `TASKS_TOKEN` in Secret Manager, readable by that account, and no Twilio or email: the preview uses the fake ones. It sets `CAUSEMATCH_FAKE_OAUTH=1` too, so the preview offers Google through the fake consent page and no Apple; real Google and Apple sign-in would need the fake removed, their secrets and the preview's URL registered (Live providers). It copies the seed (`SEED_SRC`: `orgs.json`, `logos-raw/`, `photos-raw/`) into `preview-seed/`, which git ignores and `.gcloudignore` sends, builds the `Dockerfile` with Cloud Build (`gcloud run deploy --source .`), removes `preview-seed/` again, and sets `PUBLIC_BASE_URL` to the service URL it prints: open that URL, since forms only work on that origin. One instance at most, 1 GiB, with startup CPU boost. One instance is kept warm by default (`MIN_INSTANCES=1`, about $10–15 a month), because a cold start takes about 50 seconds to reseed; `MIN_INSTANCES=0 scripts/deploy_preview.sh` lets it scale to zero when idle. The database lives in the container and is reseeded whenever an instance starts; the demo coordinator's and admin's sign-in links are in the startup log, or `/org/login` shows a new demo coordinator link on the page (and `/login` a volunteer's). The script refuses a `PROJECT` whose name isn't `Causematch` (a project id is first come, first served).

- **Anyone with the preview link can sign in as any demo volunteer by email**: `/login` shows the link on the page, as `/org/login` does a demo coordinator's, but only for the demo's addresses (`config.demo_address`), which may also sign up there. Any other address gets the same "Check your email" answer, with nothing made, shown, sent or logged, so a real address can't sign up or be signed in as there. Google sign-up stays open to testers, through the fake consent page.
- **Anyone with the preview link can act as the demo nonprofit** ("Try it as a nonprofit"), and what they change persists until the instance is replaced (a redeploy, or a restart by Cloud Run), which resets the data. While the demo is on, a like from a tester's own account is made blind, so it never reaches an org's inbox, shifts, chat or counts.
- **Anyone with the preview link can also sign in as any demo coordinator** through the fake Google consent page, which takes whatever email is typed as verified; the stand-in coordinators' addresses are easy to guess. Google needs the address's domain typed as the hosted domain; without it the page answers as `/org/login` does and shows the coordinator's link. Only the demo's domains get in this way: any other coordinator gets what an unknown address gets in production ("No nonprofit account uses this email", or without the hosted domain the "a sign-in link is on its way" notice with nothing sent). So real nonprofits use "Try it as a nonprofit", and no real claim should be approved on the preview. Admin addresses are refused there, as the emailed link is never shown for one, so the admin's sign-in link stays in the startup log.
- **Rotating the password** (a new `PREVIEW_PASSWORD` version, then redeploy) voids every access cookie and old link: the next request with an old cookie gets the 401 page, the cookie is deleted, and it counts as one wrong guess. Send the new link. A browser that still sends Basic credentials saved before the access link existed counts a wrong guess per request, so after 10 it gets 429 for up to 10 minutes: clear the site's saved credentials (or use a private window). Everyone behind one address (an office network) shares that count.
- **The seed also leaves this machine**: `gcloud run deploy --source .` uploads the build context, `preview-seed/` included, to the Cloud Build source bucket (`gs://run-sources-<project>-<region>`), and the image holding it stays in Artifact Registry (`cloud-run-source-deploy`). Both are private to the project; delete old ones, or set a lifecycle rule on the bucket, when the preview goes away.

**Smoke test.** After each deploy, run `scripts/smoke_preview.py` against the preview: it walks the presenter's path in a phone-sized browser (the access gate, "Try it as a volunteer", the deck's "Confirms your hours" chip, a like and its match, confirmed hours, a certificate with its PDF and check link, "Try it as a nonprofit" with the volunteer in its inbox and its shifts, `/privacy`), prints `ok` or `FAIL` per step and exits 1 if any failed. Read the password from Secret Manager into the environment in the same shell, so it is never typed, printed or saved:

```
PREVIEW_PASSWORD="$(gcloud secrets versions access latest --secret PREVIEW_PASSWORD --project causematch-la)" \
  uv run python scripts/smoke_preview.py "$URL" [--screenshots DIR]
```

`URL` is the bare `https://` address the deploy printed, without `?access=`; the script refuses a URL that has it, and a missing password. A run makes two demo copies of the volunteer, and an address may make 10 an hour. In a preview the access gate also covers `/check/...`, so the check link answers 401 without the access cookie; the script expects that. `--insecure` accepts a self-signed certificate, for running against a local preview served with its own (a preview refuses `http://` origins).

### Schema changes

Adding a column or a table: edit the class in `app/db.py` (`transform=True` does the rest). Renames, data changes, index changes and anything touching triggers need a numbered migration in `app/migrations/` instead; its docstring says how. Pending migrations run at startup, or by hand with `uv run python -m app.migrations [--db PATH]`.

### Secret scan

`scripts/secret_scan.sh` runs gitleaks with `.gitleaks.toml` over the git history.

## Admin

Orgs start unverified and their openings stay out of every deck until an admin approves them at `/admin/orgs` (EIN checked against ProPublica) or with `scripts/verify_org.py`. Reports, suspensions, org deactivation, removing a reported volunteer's photo and unblocking are in `/admin/reports` and `/admin/blocks`. Nonprofits come from [ProPublica Nonprofit Explorer](https://projects.propublica.org/nonprofits/) (IRS public data): `scripts/import_orgs.py --city "Los Angeles" --state CA` imports a sample of Los Angeles ones (any LA County city works), `--ein` imports one, and a coordinator asks for access at `/org/claim` (an admin approves at `/admin/claims`). A report from a volunteer names an org, so to remove one coordinator use `scripts/remove_coordinator.py`.
